## Requirements

### Requirement: P0 真实外部链路验收

系统 SHALL 在宣布第三方模型或通知可用前，通过实际产品入口完成验证，保存可追溯且脱敏的结果。

- [ ] 使用用户选定且已配置凭据的第三方模型，分别完成连接测试、真实材料分析、引用校验、报告持久化和再次打开；不能以本机兼容接口或 HTTP 桩代替供应商验收。
- [ ] 经用户明确同意，向指定接收端发送一次测试摘要，核对服务回执与实际收到的内容；若渠道不提供已读/送达确认，应分别记录服务接受和接收端确认，不推断已经送达。
- [ ] 记录应用版本、时间、供应商/协议/模型、脱敏 run_id、结果与限制；不保存密钥、授权头或带凭据的端点。受凭据、访问权限、余额或接收端限制的项目保持未完成。

当前缺口：用户选择 ZCode API Key，并要求可切换 Codex；多 API 配置及默认提供者切换已存在，ZCode 的具体端点/模型与密钥仍待配置。Telegram 未配置；WhatsApp 有本机配置字段但未启用、有效性未验证，最终验收渠道和接收端尚待确认。Telegram/WhatsApp 的渠道选择已确定，但名称选择不代替真实接收验收；密钥在本机配置，不写入本文件。

实现落点：[模型与研究服务](../../../research/service.py)、[每日摘要](../../../research/digest.py)、[通知通道](../../../notifier)。这里验收现有链路，不重做模型配置或摘要功能。

#### Scenario: 连接成功但真实分析失败
- **WHEN** 连接测试成功，但材料分析超时、引用校验失败或未成功入库
- **THEN** 记录实际失败阶段，模型分析验收仍未完成，不将连接成功显示成完整可用。

#### Scenario: 通道接受与用户收到不一致
- **WHEN** 通道返回接受回执，但没有接收端确认
- **THEN** 保留“服务已接受、接收尚未确认”的区别，不能勾销通知实际接收验收。

### Requirement: P0 持续运行与故障恢复验收

系统 SHALL 用实际运行记录验证可信沉默、跨日稳定和可恢复性；源码测试、安装产物检查与真实连续运行是不同证据。

- [ ] 完成真实 30 天观察，覆盖港美交易日历与预期扫描窗口、SLO、外部 watcher、启动/重启、通知和跨日采集；注明运行版本、观察窗口及未覆盖情况。关键缺陷修复后的受影响窗口重新观察，不拼接成虚假的连续通过。
- [ ] 用真实运行窗口校准多窗口 burn rate 阈值，确认 UNKNOWN/降级不能被旧数据或 AI 提升成正常履责；离线故障演练不能替代真实阈值校准。
- [ ] 在用户下一次真实登录后验证自动启动。当前已通过已安装 Guardian 的 LaunchAgent 注册、真实启动、受控重启（不同 PID）和 SpaceX 研究关注记录保留验证；这不替代实际退出登录后重新登录。本轮升级后首次就绪检查超出 60 秒等待窗口，随后鉴权检查确认 RUNNING；SEC 版本升级时再次出现就绪等待偏长，最终 RUNNING；仍需记录并排查启动耗时，并完成真实登录验证，不能把最终可连接当作时延问题已修复。
- [ ] 对已准备的 12 项[质量材料包](../../../tests/fixtures/research_quality/corpus.json)完成人工审校，并补真实音频转写验收。现有建议标签仍待人工签核；离线评分不调用模型，默认费用为零；真实模型每轮最多 2 次调用、1 美元，须先证明 token/单价上限，保留误报、漏报、弃答与缺失项。

实现落点：[可靠性职责](../../../reliability)、[现有可靠性说明](../../../docs/RELIABILITY.md)、[研究服务](../../../research/service.py)。不新增第二套调度器或可观测平台。

#### Scenario: 停机或网络失败跨过扫描窗口
- **WHEN** Guardian 停机或来源不可用导致预期窗口缺口
- **THEN** 缺口可追溯，状态和通知如实表达；恢复后按现有履责条件恢复，不能仅靠重启变绿。

### Requirement: P3 可用的未来财报与分红来源

系统 SHALL 接入覆盖和访问条件明确的自动事件来源，先完成一个市场的真实产品路径验证，再扩展其他市场。

- [ ] 选定可实际使用的来源，记录市场、事件类型、未来/历史覆盖、更新频率、访问要求与请求额度。当前 Yahoo 历史行动源在 2026-10-16 的产品实测为 permission_required（HTTP 401/403）；可用自动源验收仍未完成，不能以失败回执宣称成功。
- [ ] 接入未来财报：分开记录披露日期、财务期间、盘前/盘后等时段；没有精确时间就保持 event_at 为空。预计日期不得写成正式已披露。
- [ ] 接入来源实际覆盖的未来分红，复用公告/除息/登记/派息四日期；保留金额、币种及缺失值，历史分红成功不能冒充未来日历可用。
- [ ] 适配器按参数校验→有界获取→业务状态检查→标准事件转换分层；为请求跨度、页数、并发、重试、总耗时和返回体设上限。复用当前显式刷新/停止、版本及失败保留旧记录机制；新来源必须接入按证券、类型、日期范围记录的覆盖状态，定义自己的新鲜度预算，缓存不能刷新原始取得时间。
- [ ] 优先使用来源稳定事件 ID；缺少 ID 时，只有来源契约能支持的证券/财季等稳定组合才可用，不把可变事件日期做身份，也不凭猜测合并改期事件。跨来源相似记录保留来源关联，不直接覆盖。
- [ ] 用实际可访问来源验证获取、解析、入库、界面可读及重复刷新；保留原文链接与时间。不能获得来源时保持未完成并清楚提示支持范围，人工导入不作为自动来源验收替身。

来源前置核查（2026-10-15）：Nasdaq 未来日历仍缺可确认的自动获取许可，尚未取得业务数据样本；先确认可用来源及访问范围，再实现和实测，不能把公开接口地址当作可用保证。参考 [Nasdaq 条款](https://www.nasdaq.com/legal)。

实现落点：[来源适配](../../../research/event_sources.py)、[事件存储](../../../research/events.py)。源码依据：[OpenBB 财报适配](https://github.com/openbq-org/OpenBB/blob/7c9d4221bdf66965e3f6c7f4dc6ee848073e5ae2/openbb_platform/providers/nasdaq/openbb_nasdaq/models/calendar_earnings.py)、[分红适配](https://github.com/openbq-org/OpenBB/blob/7c9d4221bdf66965e3f6c7f4dc6ee848073e5ae2/openbb_platform/providers/nasdaq/openbb_nasdaq/models/calendar_dividend.py)。其按日取数和字段分层是参考，接口当前可用性必须独立验证。

#### Scenario: 未来财报只有日期与盘后标签
- **WHEN** 来源返回下周某日盘后发布财报及对应财季
- **THEN** 展示预计披露日、盘后标签和独立财季；不生成精确午夜，不把财季结束日当披露日；改期后可追溯原计划。

#### Scenario: 来源只提供历史行动
- **WHEN** 用户查看未来财报或未来分红，而配置的来源仅支持历史分红/拆股
- **THEN** 显示该类型/期间不受支持，不能展示“未来没有事件”或“已更新”。

### Requirement: P3 正式公司披露来源

系统 SHALL 将正式披露和未来事件计划区分，先完成支持范围内的真实原文验收，再扩市场。

- [ ] 解决或确认 SEC 原文的合规访问条件，并在实际桌面入口验证至少一份原文可读；2026-10-16 已安装 Guardian 经真实 IPC 自动取得并保存 SpaceX（SPCX）9 份正式披露，但抽查原文返回 permission_required，不能宣称原文验收通过。
- [ ] 扩展其他美股前验证证券映射来源。当前 SPCX 使用经官方 submissions 验证的 CIK 种子，每次仍核对返回 CIK 和 ticker；其他证券依赖官方代码表，该表目前受限，不宣称全市场可用。

已有适配、独立提交身份、接收时间精度、分页/失败保留及桌面入口的使用说明见 [研究说明](../../../docs/RESEARCH.md)，不再重复列为待实现。SEC 已提交披露不能充当未来公告日程。参考 [SEC 接口说明](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)。

源码依据：[OpenBB SEC 公司披露](https://github.com/openbq-org/OpenBB/blob/7c9d4221bdf66965e3f6c7f4dc6ee848073e5ae2/openbb_platform/providers/sec/openbb_sec/models/company_filings.py)、[披露测试](https://github.com/openbq-org/OpenBB/blob/7c9d4221bdf66965e3f6c7f4dc6ee848073e5ae2/openbb_platform/providers/sec/tests/test_company_filings.py)。不能仅凭其 accepted_date 字段名推断已保证精确时间契约。

#### Scenario: 目录已取得但原文访问失败
- **WHEN** 披露目录获取成功，原文返回访问限制
- **THEN** 保留目录记录和原文链接，明确原文尚未验证可读，不将整体验收标为完成。

### Requirement: P4 可解释的集中度

系统 SHALL 在持仓快照上计算可追溯的单股、币种和有覆盖说明的行业集中度，并显示估值完整性。

- [ ] 先提供单股及币种占比、前 N 大持仓和用户设定阈值；行业聚合随后加入，必须标注分类来源、版本/时间及未分类部分，不将未分类塞进其他已知行业。
- [ ] 市值=数量×同币种有效报价；统一基准币种时记录汇率来源、报价与汇率时间、换算方向和新鲜度。缺价、缺汇率或过期时显示不可估/过期及缺失证券，不用 0 填充。
- [ ] 明确分母范围；组合不完整时可以展示“已估值部分”的占比，但不能称完整组合占比。用户输入成本可单独用于成本口径，不混成市值口径；报价币种构成不能称为完整经济风险敞口。
- [ ] 取价/汇率显式触发并有调用预算；页面只读。首版不计算投资收益、胜率、税费或自动调仓，不发送新的集中度提醒。

源码依据：[Ghostfolio 活动到快照](https://github.com/ghostfolio/ghostfolio/blob/4921c001ba75146d2df060ff754bebb18ad64828/apps/api/src/app/portfolio/portfolio.service.ts#L637)、[持仓占比](https://github.com/ghostfolio/ghostfolio/blob/4921c001ba75146d2df060ff754bebb18ad64828/apps/api/src/app/portfolio/portfolio.service.ts#L762)、[币种集中度](https://github.com/ghostfolio/ghostfolio/blob/4921c001ba75146d2df060ff754bebb18ad64828/apps/api/src/models/rules/currency-cluster-risk/current-investment.ts#L31)。其[分组实现](https://github.com/ghostfolio/ghostfolio/blob/4921c001ba75146d2df060ff754bebb18ad64828/apps/api/src/models/rule.ts#L43)出现 marketPrice ?? 0；本项目不采用缺价归零的降级方式。

#### Scenario: 港美混合持仓缺少一组汇率
- **WHEN** 用户查看统一币种集中度，但一笔港股缺少有效换算汇率
- **THEN** 显示组合估值不完整及缺失项；不把该持仓计成零，不输出貌似完整的组合百分比。

## Implementation constraints

延续 PySide 桌面→鉴权本地 IPC→Guardian→现有 SQLite/规则配置的职责。密钥不进入记录，读取页面不联网，新增外部调用显式启动且可取消；任何来源、模型、缓存或人工“已核验”状态都不能改变原始证据或代替真实性证明。持仓集中度按后续阶段实施；自动交易、多用户平台、Web 重构和新增队列均不在本清单范围。

每个工作包完成时，检查必要的服务边界与实际 UI/CLI 行为，更新使用说明，并删除本文件内已完成条目。文档整理只需验证单文件约束、链接和 OpenSpec 格式；产品修改再按风险运行对应行为测试及项目门禁。
